# Lessons: working with the user

Evidence: the user's words in session. Format: one line each, `- <YYYY-MM-DD> · When <situation>, <do this>, because <reason>.`

- 2026-10-29 · When presenting a plan, lead with one picture of how it works and one walked-through example, because the user has little time to read everything.
- 2026-10-29 · When a plan or delivery uses a new idea, teach it at the architecture level (what, how it works, the thinking, why here, when not), because the user wants to learn something with every plan.
- 2026-10-29 · When asking, print questions in chat in small batches whose answers do not affect each other, each with a recommended option and its reason, then rewrite the next batch from the answers, because answers reshape later questions.
- 2026-10-29 · Never ask what the project already answers, such as coding rules or the environment, because obvious questions waste the user's time; ask about data sources, services, and side effects instead.
- 2026-10-29 · In a summary, place every choice and edge case on the step it affects without saying who decided it, because the user judges the plan, not its author.
- 2026-10-29 · When the chat can render HTML, show visuals as HTML without being asked; otherwise use text diagrams, because the user rarely asks for a visual.
- 2026-10-29 · Keep additions inside the goal (prepare the terrain, do not build the house), because wide additions point the next session the wrong way.
- 2026-10-29 · Do not treat a merged PR as proof the work was right; the user's feedback over time is, because the user may merge and still want it different.
- 2026-10-30 · Keep orchestration, subagent, and model instructions out of rules and skills unless the user asks for them, because the user wants only the rules that apply.
